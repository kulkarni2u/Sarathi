# Sarathi Repo Wiki Design

## Goal

Add a Sarathi-native repo wiki generator that creates a language-agnostic
Markdown map of a repository under `.sarathi/wiki/`. The wiki should be created
as part of `sarathi init` and refreshable later through a standalone command.

The feature should feel like policy packs: explicit, auditable, repo-local, and
not dependent on a hosted model or a third-party graphing library.

## Current Behavior

`sarathi init` currently generates `policy-pack/`, writes provider permission
config, validates the policy pack, and optionally bootstraps NCP. It does not
create `.sarathi/wiki/`.

The service workspace bootstrap path can create top-level docs such as
`wiki/README.md`, but that is a separate onboarding path and not the CLI init
contract.

## Target Behavior

`sarathi init [target_path]` should bootstrap two repo-local knowledge layers:

- `policy-pack/`: governance and execution policy.
- `.sarathi/wiki/`: generated repository map for agents and humans.

The init flow becomes:

1. Inspect repository.
2. Interview or choose defaults.
3. Generate policy pack.
4. Generate repo wiki.
5. Validate.
6. Evolve.

When `--ncp` is passed, NCP setup remains an additional step after the core init
flow.

## CLI Contract

- `sarathi init [target_path]`: generate policy pack and `.sarathi/wiki/`.
- `sarathi init [target_path] --no-wiki`: skip wiki generation.
- `sarathi wiki [target_path]`: generate or refresh `.sarathi/wiki/`.
- `sarathi wiki [target_path] --check`: report whether the wiki exists and is
  current enough to be useful, without writing files.

The default target path is `.` for both commands.

## Skill Shape

The repo wiki should be implemented as a Sarathi-native skill/capability, not as
a wrapper around a third-party graphing tool.

Recommended structure:

```text
src/repo_wiki/
  __init__.py
  generator.py
  inventory.py
  extractors/
    __init__.py
    base.py
    generic.py
    java.py
    javascript.py
    python.py
  renderers/
    __init__.py
    markdown.py
    mermaid.py
```

The agent-facing skill guidance should live in the portable Sarathi skill pack,
for example as `skill/reference/repo-wiki.md`, with a short pointer from
`skill/SKILL.md`. The guidance should explain when to refresh the wiki, what the
generated files mean, and how agents should use them before starting repo work.

## Language-Agnostic Core

The core inventory should work for any repository by using:

- directory layout
- file extensions
- project manifests
- common source and test path conventions
- obvious entry-point files
- generated-file and dependency-directory ignores

Language-specific extractors are optional enrichers. They should never be
required for the wiki to generate.

Initial enrichers:

- Generic fallback: paths, extensions, manifests, test/source grouping.
- Python: packages, modules, imports, common test files.
- Java: Maven/Gradle manifests, packages, classes/interfaces/enums/records,
  imports, source/test/resource roots.
- JavaScript/TypeScript: package scripts, imports/exports, source/test grouping.

The Java extractor should parse source text with lightweight standard-library
logic. It should not require Maven, Gradle, javac, or a Java parser dependency.

## Generated Files

Write generated artifacts under `.sarathi/wiki/`:

```text
.sarathi/wiki/
  index.md
  structure.md
  modules.md
  dependency-graph.md
  testing.md
  generated.json
```

`index.md` summarizes the repository: detected languages, build systems, major
directories, entry points, and links to the other wiki files.

`structure.md` lists top-level directories and important file groups.

`modules.md` describes detected packages/modules by language and path.

`dependency-graph.md` renders a Mermaid graph plus an adjacency list. This is a
static architecture graph, not a full method-level call graph.

`testing.md` summarizes detected tests, test frameworks, and likely test
commands.

`generated.json` stores the same inventory in machine-readable form for future
Sarathi phases.

## Write Safety

Every generated Markdown file should include a marker:

```text
<!-- generated by sarathi wiki -->
```

Sarathi may overwrite files with that marker during refresh. If a file exists
without the marker, Sarathi should preserve it and report that it was skipped.

`generated.json` is always generated data and may be overwritten.

## Model And Dependency Policy

Version 1 uses no hosted model and no third-party graph library. It should rely
on Python standard-library parsing plus small, explicit heuristics.

Future versions may add optional model summarization behind an explicit flag,
but the default wiki generation must remain deterministic and offline.

## Tests

Add focused tests for:

- `sarathi wiki .` creates `.sarathi/wiki/` and all expected files.
- `sarathi init .` creates both `policy-pack/` and `.sarathi/wiki/`.
- `sarathi init . --no-wiki` skips `.sarathi/wiki/`.
- Existing generated wiki files are refreshed.
- Existing unmarked wiki files are preserved.
- Generic repositories produce useful structure and manifest output.
- Java repositories produce package/type/import/module output.
- Python repositories produce package/module/import output.
- JavaScript/TypeScript repositories produce manifest/import output.
- `--check` exits/report-fails when wiki files are missing.

Run targeted tests first, then the broader policy-pack verification path:

```bash
python3 -m pytest tests/test_repo_wiki.py tests/test_cli.py -q
python3 -m pytest -q
python3 -m build --sdist --wheel
```

## Out Of Scope

- Third-party graph libraries.
- Full Java compiler/classpath analysis.
- Method-level call graphs.
- Model-generated prose summaries.
- Replacing the service workspace bootstrap docs.
- Moving top-level `wiki/` docs into `.sarathi/wiki/`.
